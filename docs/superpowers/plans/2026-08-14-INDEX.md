# Stakeholder Q&A Expansion — Roadmap

Three plans implementing the "Stakeholder Q&A Feature Requirements" spec: multi-turn
chat UI with history, a DataFrame-centric compute engine with a Python repair loop, and
selective storyline export. Each produces working, testable software on its own; the
order below is the dependency order.

## Why three plans and not one

The spec spans three subsystems with different risk profiles: a UI/persistence layer
(low risk — additive tables and routes), a compute-architecture change (medium risk —
introduces Python execution, needs a real sandboxing/policy story), and a document
generator (low risk, but depends on both of the others existing first). Bundling them
would mean reviewing "add a table" alongside "decide how untrusted-ish LLM-written
Python gets executed safely" in one diff.

---

## 1. Stakeholder Conversations & Chat UI — [plan](2026-08-14-stakeholder-conversations-ui.md)

**The problem:** `StakeholderService.answer()` is stateless (no `conversation_id`
anywhere in the service, the API, or the schema) and the frontend is a single-turn
widget — one question, one answer, overwritten by the next question, lost on refresh.
There is no chat history, no thumbs-up/down UI (the backend endpoint exists and is
unused), and generated SQL renders as a plain, non-collapsible `<pre>` block.

**The fix:** a `stakeholder_conversations` table plus a `conversation_id` column on
`stakeholder_answers`; `answer()` takes an optional `conversation_id` and auto-creates
one on the first turn; new list/get/rename/star/delete conversation routes; a rebuilt
frontend chat surface with a history sidebar, a scrollable multi-turn thread, wired-up
feedback buttons, and collapsible code blocks for generated SQL.

**9 tasks.** No dependency on plans 2/3 — this lands first and everything else threads
through the `conversation_id` it introduces.

## 2. DataFrame Compute Engine & Python Repair Loop — not yet planned

**The problem:** every execution path (`SamplerExecutor`, `BrowserSessionExecutor`) only
runs SQL text. The spec calls for a multi-turn session that dynamically chooses between
re-running SQL and running Python against an already-fetched, cached DataFrame — with an
automatic error-repair loop mirroring `_synthesize_and_execute_sql`'s SQL retry loop —
under a strict local-compute-only policy (raw data never leaves the process; only
aggregated findings reach the LLM).

**Why this isn't detailed yet:** it needs plan 1's `conversation_id` to know which
DataFrames are in scope for a given thread, and a real decision on the Python execution
sandbox (subprocess with a resource-limited interpreter vs. a restricted in-process
`exec` vs. an existing sandboxing library) belongs in its own plan, not bolted onto the
UI plan. Write this plan once plan 1 is merged and the conversation model it threads
through actually exists.

## 3. Storyline Export (Report Builder, Word/Markdown) — not yet planned

**The problem:** no export surface exists at all today — no Report Builder side-panel,
no drag-and-drop/checkbox turn selection, no `.docx`/Markdown generation, no
dependency-tracked Code Appendix, no proactive 50,000-token warning.

**Why this isn't detailed yet:** "selective storyline export" operates over the chat
history plan 1 introduces, and the Code Appendix's "dependency tracking" needs plan 2's
Python-cell model (a cell can depend on a DataFrame produced by an earlier cell) to mean
anything precise. Plan after 1 and 2.

---

## Suggested order

1 → 2 → 3. Plan 1 is fully specified and ready to execute now; 2 and 3 get written once
the plan before them has landed and its actual interfaces are known, rather than
guessing at them in advance.

## Conventions used by all three plans

- Every task is TDD: failing test, verify the failure, minimal implementation, verify
  the pass, commit.
- Run everything from the repo root with `.venv/bin/python` (backend) / `npm` inside
  `frontend/` (frontend).
- No feature branches — every task commits directly to `main` (standing project
  convention; see persistent memory `no-feature-branches-work-on-main`).
- New tables: add to `TENANT_SCHEMA` in `analytics_platform/database.py`
  (`CREATE TABLE IF NOT EXISTS` is enough for a brand-new table). New columns on an
  existing table: add a non-destructive `ALTER TABLE ... ADD COLUMN` in `_migrate()`,
  following the existing `queries_run` migration as the template.
- No silent failures: log a warning and surface a user-facing caveat rather than
  silently dropping/defaulting, matching the convention already in
  `resolve_template_placeholders`/`_refresh`.
- Every tenant's data lives in its own SQLite file — all new queries scope by
  `tenant_id` as defence-in-depth, but the file boundary is what actually isolates.
