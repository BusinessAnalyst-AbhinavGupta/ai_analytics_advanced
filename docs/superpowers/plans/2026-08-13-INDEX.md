# Remediation Roadmap — Tenancy, Brain & Skills

Five plans covering every gap found in the 13 Aug 2026 architecture evaluation, plus the
per-tenant database isolation the evaluation got wrong. Each produces working, testable
software on its own; the order below is the dependency order.

## Why five plans and not one

The work spans five subsystems with different owners and different risk profiles.
Bundling them would mean a single review gate over changes ranging from "fix a regex" to
"change where every company's data lives." Each plan below is separately reviewable and
separately revertible.

---

## 0. Tenant Store Isolation — [plan](2026-08-13-tenant-store-isolation.md)

**The problem:** every tenant is a different company, but the isolation boundary is a
`WHERE tenant_id = ?` clause, not a file. `run_dashboard.command tenants/DTDL` exports
`ANALYTICS_DATA_DIR` and does give DTDL its own database — but that is a launcher
convention, not an invariant. The default path, `data/platform.db`, currently holds four
tenants co-mingled in one file. The difference between isolated and mixed is one
environment variable being set correctly.

**The fix:** split the schema into a control plane (`tenants`, `scheduler_state`,
`api_logs`, `auth_principals` — one file) and a tenant plane (the other fifteen tables —
one file per company at `tenants/<id>/tenant.db`). A `TenantStoreProvider` maps
`tenant_id → Store`, caches connections, refuses ids that escape the tenants root, and
records each database's owner so opening company A's file as company B raises
`TenantIsolationError` instead of silently mixing them. Services hold the provider and
resolve a store per call.

**Why this shape:** it serves both deployment models without a fork — one process for all
companies, or one process per company, same code. Per-tenant export, backup and deletion
become one filesystem operation. Existing `tenant_id` columns stay as defence-in-depth
behind the file boundary.

**6 tasks.** Do this first: it changes where the other plans' tables live.

> **Correction on the record.** The original evaluation argued against per-tenant files,
> reasoning that the SQL pre-filter was sufficient and a split too risky. That was wrong.
> If tenants are separate companies, a shared file is not isolation regardless of how
> careful the queries are — a single missing `WHERE` clause, or a mis-set env var, mixes
> two customers' data. This plan supersedes that recommendation.

## 1. Brain Retrieval Rebuild — [plan](2026-08-13-brain-retrieval-rebuild.md)

**The problem:** semantic search has never executed. The vector index is wired into one of
twelve construction sites and the Stakeholder Analyst is not one of them; where it is
wired, the Chroma query raises `ValueError: Expected where to have exactly one operator`
on every call and a bare `except: pass` hides it. Retrieval silently degrades to
`title LIKE '%<the user's entire question>%'`, which matches nothing, so the Brain reports
itself empty no matter how much you curate.

**The fix:** replace ChromaDB with SQLite-native hybrid retrieval — FTS5/BM25 for the
lexical leg, normalised embeddings in a BLOB column for the dense leg, fused by Reciprocal
Rank Fusion, re-ranked on stored confidence. Both tables live in the tenant's own database
from plan 0. Zero new dependencies; it removes one.

**Why this shape:** at a few thousand curated nodes per tenant an ANN index earns nothing
measurable, while a second stateful store costs a dual-write drift problem, a shared
cross-tenant collection, and a 1.3 GB model default. Both legs exist because they fail
differently: BM25 carries internal vocabulary (`BC2D`, city names, product codes) that
embeddings handle poorly, and embeddings carry paraphrase that BM25 cannot see.

**9 tasks.** Depends on plan 0 for `TENANT_SCHEMA` and the store provider.

## 2. Brain Governance — [plan](2026-08-13-brain-governance.md)

**The problem:** `AGENTS.md` says humans approve knowledge before it becomes company fact.
Three code paths disagree. The junior self-approves its own low-level findings (cap 500)
despite a docstring claiming it never writes the Brain;
`POST /knowledge/{t}/{n}/review` calls `brain.approve` with no `AuthGate` and a
caller-supplied `by` string; the AI senior prompts an LLM for a verdict and then approves
unconditionally, recording the model's assessment as a note. Two further write paths call
methods that do not exist — `bulk_ingest_json` crashes on `brain.save`, and
`evaluate_kpis` fails into a bare `except`, so proactive KPI monitoring has never fired.

**The fix:** auto-promotion becomes an opt-in, default-off tenant setting that leaves
findings at `UNDER_REVIEW` when disabled; the review endpoint takes its reviewer identity
from a verified principal; the AI verdict is parsed and decides, defaulting unparseable
output to `revise` rather than `approve`; the two dead paths are repaired with tests that
fail if they regress to silence.

**5 tasks.** Task 1 references `CompanyBrain(..., index=...)` from plan 1 Task 8 — run it
after plan 1, or use the two-argument form and revisit.

## 3. Skills Portability — [plan](2026-08-13-skills-portability.md)

**The problem, and the one most relevant to running across organisations:** the only
analytics skill has never executed — the engine substitutes `$key` while every template
uses `{{KEY}}`, so the literal `{{STEP_1_PAGE}}` goes to the warehouse. And that skill
hardcodes `eshop_data.es_events_v2`, `nc = 'de'` and one organisation's column names in
the shared repository, offered to every tenant. Structurally, skills only run when the
Brain returns nothing, so they become unreachable as the Brain improves; and successful
runs are discarded rather than filed for review.

**The fix:** a skill declares an abstract **data contract** ("an event stream with an
entity, a step and a timestamp"); each tenant supplies a **binding** mapping it onto real
tables, gitignored at `tenants/<id>/skill_bindings.json` — beside that company's
`tenant.db`, so its whole footprint is one directory. The SQL template becomes
byte-identical for every organisation. The registry only offers skills the current tenant
can satisfy, is anchored to the repo rather than the CWD, and excludes non-analytics
skills. Skill selection becomes orthogonal to Brain hits, and results land as `CANDIDATE`
findings.

**Why this shape:** onboarding organisation number four should be writing a bindings file,
not forking SQL — and a method improvement should reach every customer at once. That is
the class/object model `AGENTS.md` describes, applied to skills.

**5 tasks.** Independent of plans 1 and 2; the binding path assumes plan 0's layout.

## 4. Frameworks & Confidence — [plan](2026-08-13-frameworks-and-confidence.md)

**The problem:** the four friction types and the Metrics Tree return **zero** grep hits
across the codebase — the frameworks that most distinguish this from generic text-to-SQL
are documentation no model has ever seen. Separately, of six confidence dimensions only
two are ever updated; `freshness` is pinned at 1.0 forever yet is read for ranking, so
ranking sorts on a constant. `AGENTS.md` also names a `data_quality` dimension that does
not exist.

**The fix:** one versioned `frameworks.py` feeding the stakeholder and junior prompts,
plus a validator that flags a driver recommendation with no guardrail (reporting only — it
never fabricates a missing section). Freshness decays exponentially and is derived on
read; evidence is seeded from a node's backing run; a scheduled sweep marks decayed nodes
stale; the documented and stored dimension sets are reconciled.

**4 tasks.** Depends on plan 1 Task 7 for the ranking change.

## Suggested order

0 → 1 → 2 → 3 → 4.

Plan 0 first because it decides where every table lives, and doing it after plan 1 would
mean moving the new index tables twice. Plan 1 next because it is the live pain, and a
working retrieval baseline makes every later change measurable. Plans 2 and 3 are
independent of each other — run them in parallel if two people are available. Plan 4 last,
since its ranking change lands on plan 1's `search()`.

## Conventions used by all five plans

- Every task is TDD: failing test, verify the failure, minimal implementation, verify the
  pass, commit.
- Run everything from the repo root with `.venv/bin/python`.
- Every `except` touched must log; a bare `except: pass` is a review rejection. That defect
  class is what hid all of this.
- Existing tests that assert the old (defective) behaviour get updated in the same commit,
  with a comment naming the plan and why the old expectation was wrong.
