# Remediation Roadmap — Brain & Skills

Four plans covering every gap found in the 13 Aug 2026 architecture evaluation. Each
produces working, testable software on its own and can be executed independently, but
the order below is the dependency order.

## Why four plans and not one

The evaluation spans four subsystems with different owners and different risk profiles.
Bundling them would mean a single review gate over changes that range from "fix a regex"
to "change what counts as an approved company fact." Each plan below is separately
reviewable and separately revertible.

---

## 1. Brain Retrieval Rebuild — [plan](2026-08-13-brain-retrieval-rebuild.md)

**The problem:** semantic search has never executed. The vector index is wired into one
of twelve construction sites and the Stakeholder Analyst is not one of them; where it is
wired, the Chroma query raises `ValueError: Expected where to have exactly one operator`
on every call and a bare `except: pass` hides it. Retrieval silently degrades to
`title LIKE '%<the user's entire question>%'`, which matches nothing, so the Brain
reports itself empty no matter how much you curate.

**The fix:** replace ChromaDB with SQLite-native hybrid retrieval — FTS5/BM25 for the
lexical leg, normalised embeddings in a BLOB column for the dense leg, fused by
Reciprocal Rank Fusion, re-ranked on stored confidence, behind a SQL pre-filter that
makes tenant isolation an invariant of the source of truth. Zero new dependencies; it
removes one.

**Why this shape:** at a few thousand curated nodes per tenant an ANN index earns nothing
measurable, while a second stateful store costs a dual-write drift problem, a shared
cross-tenant collection, and a 1.3 GB model default. Both legs exist because they fail
differently: BM25 carries internal vocabulary (`BC2D`, city names, product codes) that
embeddings handle poorly, and embeddings carry paraphrase that BM25 cannot see.

**9 tasks.** Start here — it is the blocker you are feeling, and it is the only plan
whose absence makes the others hard to evaluate.

## 2. Brain Governance — [plan](2026-08-13-brain-governance.md)

**The problem:** `AGENTS.md` says humans approve knowledge before it becomes company
fact. Three code paths disagree. The junior self-approves its own low-level findings
(cap 500) despite a docstring claiming it never writes the Brain;
`POST /knowledge/{t}/{n}/review` calls `brain.approve` with no `AuthGate` and a
caller-supplied `by` string; the AI senior prompts an LLM for a verdict and then approves
unconditionally, recording the model's assessment as a note. Two further write paths call
methods that do not exist — `bulk_ingest_json` crashes on `brain.save`, and
`evaluate_kpis` fails into a bare `except`, so proactive KPI monitoring has never fired.

**The fix:** auto-promotion becomes an opt-in, default-off tenant setting that leaves
findings at `UNDER_REVIEW` when disabled; the review endpoint takes its reviewer identity
from a verified principal; the AI verdict is parsed and decides, defaulting unparseable
output to `revise` rather than `approve`; the two dead paths are repaired with tests that
fail if they regress to silence.

**5 tasks.** Independent of plan 1, but its Task 1 references `CompanyBrain(index=...)`
from plan 1 Task 8 — do plan 1 first or use the two-argument form and revisit.

## 3. Skills Portability — [plan](2026-08-13-skills-portability.md)

**The problem, and the one most relevant to running across organisations:** the only
analytics skill has never executed — the engine substitutes `$key` while every template
uses `{{KEY}}`, so the literal `{{STEP_1_PAGE}}` goes to the warehouse. And that skill
hardcodes `eshop_data.es_events_v2`, `nc = 'de'` and one organisation's column names in
the shared repository, offered to every tenant. Structurally, skills only run when the
Brain returns nothing, so they become unreachable as the Brain improves; and successful
runs are discarded rather than filed for review.

**The fix:** a skill declares an abstract **data contract** ("an event stream with an
entity, a step and a timestamp"); each tenant supplies a **binding** mapping it onto real
tables, gitignored under `tenants/`. The SQL template is byte-identical for every
organisation. The registry only offers skills the current tenant can satisfy, is anchored
to the repo rather than the CWD, and excludes non-analytics skills. Skill selection
becomes orthogonal to Brain hits, and results land as `CANDIDATE` findings.

**Why this shape:** onboarding organisation number four should be writing a bindings
file, not forking SQL — and a method improvement should reach every customer at once.
That is the class/object model `AGENTS.md` describes, applied to skills.

**5 tasks.** Independent of plans 1 and 2.

## 4. Frameworks & Confidence — [plan](2026-08-13-frameworks-and-confidence.md)

**The problem:** the four friction types and the Metrics Tree return **zero** grep hits
across the codebase — the frameworks that most distinguish this from generic text-to-SQL
are documentation no model has ever seen. Separately, of six confidence dimensions only
two are ever updated; `freshness` is pinned at 1.0 forever yet is read for ranking, so
ranking sorts on a constant. `AGENTS.md` also names a `data_quality` dimension that does
not exist.

**The fix:** one versioned `frameworks.py` feeding the stakeholder and junior prompts,
plus a validator that flags a driver recommendation with no guardrail (reporting only —
it never fabricates a missing section). Freshness decays exponentially and is derived on
read; evidence is seeded from a node's backing run; a scheduled sweep marks decayed nodes
stale; the documented and stored dimension sets are reconciled.

**4 tasks.** Depends on plan 1 Task 7 for the ranking change.

---

## Suggested order

1 → 2 → 3 → 4. Plan 1 first because it is the live pain and because a working retrieval
baseline makes every later change measurable. Plans 2 and 3 are independent of each other
— run them in parallel if two people are available. Plan 4 last, since its ranking change
lands on plan 1's `search()`.

## Conventions used by all four plans

- Every task is TDD: failing test, verify the failure, minimal implementation, verify the
  pass, commit.
- Run everything from the repo root with `.venv/bin/python`.
- Every `except` touched must log; a bare `except: pass` is a review rejection. That
  defect class is what hid all of this.
- Existing tests that assert the old (defective) behaviour get updated in the same commit,
  with a comment naming the plan and why the old expectation was wrong.
